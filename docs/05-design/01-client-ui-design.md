# 客户端 UI 设计规范

适用范围：MAUI Client、Blazor Hybrid、Blazor WebAssembly

## 1. 文档目的

本规范用于统一 DevNexus 客户端在桌面端与 Web 端的 UI 方向。

设计目标围绕可执行工作流：

1. 用户知道自己当前在做什么
2. 用户知道系统做到了哪一步
3. 用户知道失败发生在哪里
4. 用户知道接下来还能怎么继续处理

## 2. UI 总方向

客户端 UI 采用内容优先、低噪声、工具化协作界面的方向。

关键特征：

1. 浅色工作区为主，局部深色承载代码或强调内容
2. 品牌绿作为唯一主强调色，不做大面积铺底
3. 小圆角、轻阴影、轻材质感
4. 明确的结构分区与状态分层
5. 视觉服务流程，不服务装饰

## 3. 核心体验原则

### 3.1 流程清晰

界面必须帮助用户识别完整链路：

1. 输入
2. 解析
3. 执行
4. 结果
5. 继续处理

任何页面如果打断这条链路，都应优先调整信息结构，而不是先补视觉样式。

### 3.2 失败可见

失败不能只存在于日志、控制台或角落提示里。

用户必须能直接从主界面知道：

1. 哪一步失败了。
2. 为什么失败。
3. 是否能重试。
4. 是否有替代动作。

### 3.3 继续处理优先

系统产出的中间结果不能成为死路。

文件结果、任务结果、解析结果、聊天结果，都应尽量提供继续处理入口，例如：

1. 加入下一轮对话。
2. 下载文件。
3. 重试任务。
4. 打开详情。
5. 重新编辑输入。

### 3.4 能力真实

UI 不得暗示当前不存在的自动化能力，也不要把“部分完成”包装成“完整闭环”。

## 4. 视觉语言

### 4.1 视觉基线

推荐视觉基线：

1. 主背景使用浅灰与白色层次。
2. 分区依靠边框、留白、浅阴影，而不是厚重卡片堆叠。
3. 圆角基线控制在 4px 到 10px。
4. 材质感只做轻量辅助，不做大面积透明叠层。

### 4.2 不推荐的视觉方向

以下方向默认不推荐：

1. 大面积毛玻璃。
2. 重渐变、重发光、重阴影。
3. 营销页式大卡片、大留白、低信息密度布局。
4. 所有状态都长得一样，只靠一行文案区分。

## 5. 设计令牌

所有 UI 代码必须优先通过设计令牌表达，而不是散落硬编码。

## 6. 布局规范

### 6.1 默认布局

默认采用工具化布局：

1. 左侧导航或会话区。
2. 中央主内容区。
3. 右侧或局部辅助结果区。

重点不在布局新奇，而在让用户始终知道自己当前处于哪条链路和哪一个上下文。

### 6.2 布局约束

1. 避免大块固定高度。
2. 优先使用 `clamp`、`min-height`、`max-height` 与局部滚动。
3. 结果区与主区层级要清晰，但不能压过主区阅读。
4. 空状态、失败状态、加载状态必须占据真实布局位置。

## 7. 关键模块规范

### 7.1 输入区

输入区不是单纯文本框，而是上下文编排区。

必须尽量承载：

1. 文本输入。
2. 附件 chip。
3. 解析进度。
4. 失败原因。
5. 可继续动作。

### 7.2 附件 chip

附件 chip 至少要明确表达：

1. 文件是否已加入上下文。
2. 是否正在解析。
3. 是否解析失败。
4. 失败原因是否可查看。

它不能只是一个文件名标签。

### 7.3 文件任务结果卡

结果卡的首要职责是把结果变成下一步动作入口。

应优先突出：

1. 产出了什么。
2. 校验是否通过。
3. 是否可下载。
4. 是否可加入下一轮。
5. 是否可重试。

### 7.4 状态提示

必须区分三类状态：

1. 聊天生成状态。
2. 文件解析状态。
3. 文件任务执行状态。

禁止把三者统一成模糊的“处理中”。

## 8. 动效规范

1. 动效只服务状态切换、层级切换、目标定位。
2. 常规反馈时长控制在 120ms 到 220ms。
3. 避免重弹跳、重漂浮、持续发光、无意义循环动画。
4. 加载页可以保留少量品牌化动效，但不能压过正文。

## 9. 可访问性规范

1. 所有可交互元素必须具备 `focus-visible`。
2. 对比度至少达到 WCAG AA。
3. 颜色不能单独承担语义，必须辅以图标或文本。
4. 缩窄布局时优先保留关键动作和关键状态提示。

## 10. MAUI 与 Web 一致性

MAUI Client 与 Web Client 允许在宿主能力上存在差异，但以下内容必须一致：

1. 设计令牌。
2. 信息层级。
3. 状态语义。
4. 关键动作位置。
5. 失败提示逻辑。

平台差异不能演变成视觉语言分裂。

## 11. Blazor 样式作用域规范

本项目使用组件隔离样式与全局样式并存的模式。为避免拆分超大 CSS 文件后产生作用域漂移和串样式，必须遵守以下规则：

1. 组件私有样式默认留在对应的 `razor.css` 内。
2. 只有在需要跨页面复用或文件治理时，才允许拆到 `wwwroot/css`。
3. 拆到全局 CSS 后，必须补根作用域，优先 `data-ui-scope="component-name"`。
4. 禁止在全局拆分文件里使用后代标签选择器表达组件语义。
5. 父组件不得假定子组件内部 DOM 结构。
6. 评审时必须检查作用域变化和加载顺序变化。

推荐写法：

```css
[data-ui-scope="dev-studio-dock"] .dev-studio-dock__title { }
.input-box .input-box__status-chip { }
```

不推荐写法：

```css
.panel strong { }
.card p { }
.meta span { }
```

## 12. 运行态低噪工作流

聊天、终端、Swarm 与审计共同构成 DevNexus AI 的运行态主链路。该链路必须优先服务“用户判断下一步动作”，而不是展示内部诊断。

### 12.1 聊天主界面

聊天主界面只承载用户需要立即处理的信息：

1. 工具是否仍在执行、是否等待用户输入。
2. 失败工具名称、失败原因与建议动作。
3. 当前终端接管状态、工作目录和命令摘要。
4. 可继续动作，例如重试、停止、打开终端或查看结果。

以下内容默认不进入聊天主界面：

1. 成功步骤数量。
2. 事件总数。
3. 最慢工具耗时。
4. Prompt cache、StablePrefix、ToolSchema 或上下文漂移诊断。

这些诊断应进入结构化日志、维护者工具或专门排障文档，不能挤占主聊天阅读区。

### 12.2 终端面板

终端面板必须把真实运行状态置于输出文本之前，便于用户先判断能否继续操作：

1. 命令、工作目录、退出码和归档状态必须可见。
2. 等待输入必须有明确提示，并能直接把焦点交还到底部输入框。
3. 超大输出只展示保留片段，完整日志通过归档入口或分块加载查看。
4. 历史终端记录必须明确“不接管输入”，避免用户误以为还能继续交互。

终端输出区可以承载技术细节，但状态区不得退化为纯日志窗口。

### 12.3 Swarm 监控

Swarm 面板用于观察上下文工作包的执行边界，不应替代聊天主线。

必须优先展示：

1. 当前阶段与阻塞原因。
2. 失败工作包、失败原因和可重试动作。
3. 工作包依赖、文件范围、执行报告与关联终端。
4. 需要安全确认或人工处理的操作。

工作包数量、在线智能体数量、事件时间线可以保留，但它们只能作为辅助扫描信息，不能压过失败、阻塞和下一步动作。

### 12.4 审计与诊断分层

审计看板、公开 API 与数据库审计表只承载产品化审计内容：

1. 工具失败。
2. 失败原因。
3. 建议动作。
4. 是否可重试。
5. 是否需要人工介入。

Prompt 成本、缓存命中、动态上下文比例、历史消息比例、Provider Token 归一化等非产品化诊断应写入 `[AI.Prompt.Diagnostics]` 等结构化日志。除非形成明确用户价值和公开契约，否则不得进入主 UI、公开审计 API 或持久化审计表。

### 12.5 验收矩阵

| 场景 | 主界面必须可判断 | 详情入口 |
|------|------------------|----------|
| 工具失败 | 失败工具、失败原因、建议动作 | 审计详情或日志 |
| CLI 等待输入 | 当前终端正在等待输入 | 终端面板 |
| CLI 超大输出 | 输出已截断、完整日志已归档 | 终端分块日志 |
| Swarm 工作包失败 | 首个失败工作包、是否可重试 | Swarm 工作包详情 |
| Swarm 终态复盘 | 结果摘要、执行报告或失败证据是否存在 | 执行报告 Artifact |
| Swarm 启动提示 | 已进入工作包协作模式、可到 Swarm 面板查看 | Swarm 面板 |
| Prompt 成本异常 | 主界面不展示内部指标 | `[AI.Prompt.Diagnostics]` |

## 13. 评审清单

在提交 UI 改动前，至少检查以下问题：

1. 用户是否能快速判断当前流程位置。
2. 失败原因是否在主界面可见。
3. 中间结果是否可继续处理。
4. 是否仍然符合低噪工具化方向。
5. 是否出现过度装饰。
6. 是否复用了统一设计令牌。
7. 是否保持 Web 与 MAUI 的一致语义。
8. 样式拆分是否破坏 Blazor isolation。
9. 聊天、终端、Swarm 与审计是否遵循低噪分层。
10. 非产品化诊断是否留在结构化日志或维护者入口。

## 14. 默认决策顺序

当多个 UI 方案都能成立时，按以下顺序做取舍：

1. 先保证流程清晰。
2. 再保证状态可见。
3. 再保证继续处理顺手。
4. 最后才做视觉润色。
