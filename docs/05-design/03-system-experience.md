# 系统体验设计

## 1. 当前系统体验的目标

当前体验设计不再围绕早期“语义缓存系统”单点展开，而是围绕整条用户可感知链路设计：

1. 发起请求时清楚知道系统在做什么。
2. 文件进入系统后能区分语义解析和真实处理。
3. 失败时看到真实原因，而不是泛化报错。
4. 成功后结果能够自然进入下一轮。

## 2. 当前体验主线

### 2.1 聊天体验

聊天仍是统一入口，但当前重点是状态连续性：

- 流式块逐步到达。
- 生成完成时 UI 正确收口。
- 生成失败时 UI 不假死。
- 当涉及终端执行时，聊天主区以终端记录卡片承载执行痕迹，实时输出转入右侧 Sidekick 终端主视图。
- 当终端等待输入时，输入框必须明确切换到 stdin 模式，避免用户误发新一轮聊天消息。

### 2.2 文件体验

文件相关体验分为两个阶段：

1. 语义解析阶段
	- 用户看到解析中、解析完成或解析失败。
2. 文件任务阶段
	- 用户看到任务创建、执行、输出、重试和继续处理。

这两段必须被用户明确区分，否则就会误以为“上传后系统为什么没直接生成新文件”。

## 3. 失败可见原则

这是当前系统体验中的关键原则。

平台应尽可能把失败原因直接暴露到用户看得见的位置，而不是只留在日志里。

当前重点体现为：

1. 附件 chip 展示失败原因。
2. 输入区 notices 展示失败摘要。
3. 放大输入框同步展示同类信息。

## 4. 结果继续处理原则

结果不是终点，而是下一轮输入。

所以结果卡的设计重点不是“展示一堆格式特化细节”，而是：

1. 告诉用户产出了什么。
2. 告诉用户是否通过校验。
3. 让用户一键把结果继续加入下一轮。

这也是近期移除 Excel 专用映射展示后的设计收口方向。

## 5. 文件平台体验原则

当前文件平台体验遵循四个原则：

1. 原始文件是事实源。
2. SmartDocument 只是语义派生物。
3. 真实文件处理由 FileTask 和外部 runner 承担。
4. 平台负责把复杂执行过程压平为可理解的状态与结果。

## 6. Swarm 体验原则

Swarm 的体验重点不是“炫技式多智能体可视化”，而是让复杂任务更可控：

1. 可以看到工作包拓扑与阶段推进。
2. 可以看到 Agent 状态变化。
3. 可以暂停、恢复和中止。
4. 需要确认时能明确提示用户。
5. Swarm 产生的终端执行不再散落在聊天正文，而应在 Swarm 监控面板中集中呈现。

## 7. 当前最重要的体验约束

### 7.1 低噪

不要在 UI 里塞大量用户看不懂的内部术语和实现细节。

### 7.2 明确状态

上传、解析、执行、回灌、失败、重试都必须被用户感知到。

### 7.3 一致的继续动作

对话、文件结果、任务结果最终都应回到“继续处理”这个统一动作上。

### 7.4 不伪造能力

平台没做的事不能通过 UI 暗示已经做了。

因此，文件体验必须明确区分语义解析和真实文件处理。

## 8. 体验质量约束

当前体验质量由以下方向约束：

1. 让 FileTask 状态更易读。
2. 让 runner 失败原因更可见。
3. 让聊天侧终端执行的实时输出收敛到统一的终端主视图。
4. 让结果资产继续处理的入口更自然。
5. 让语义层和执行层的边界对用户更清楚。
